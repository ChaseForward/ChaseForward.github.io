在 Project 1 中，我们实现了一个 缓冲池管理;
在 Project 2 中，我们实现了一个 B+Tree；
在 Project 3 中，我们将会实现一些组件，能够使 BusTub 执行查询。

Introduction: 理解 BusTub 的架构

  1. Parser 解析器 词法分析、语法分析，根据 SQL 字符串生成原始语法树 AST
  2. Binder 绑定器 拿着 Parser 生成的语法树，做绑定 + 语义检查^[1]
  3. Planner 继续处理 Binder AST，生成合适的查询计划
  4. Optimizer 优化查询计划
    [^1]: Binder 自动将 * 扩展为表中实际的列
    在 Project 3 中，我们将亲手实现一些==执行器算子==和==查询优化规则==。Bustub 采用基于行向量查询的处理模型(Volcano Model)，每个执行器都需要实现一个 Next() 方法以获取返回的结果，最多为 BUSTUB_BATCH_SIZE 个。

火山模型的特点:

  1. 递归调用: 执行器通过调用子执行器的Next()方法来获取数据
  2. 流式处理: 每次只处理一小批数据（batch），而不是一次性加载所有数据，这种机制确保了系统在处理大规模数据时仍能稳定运行。

Task 1 一些执行算子的实现

SeqScan: 顺序扫描

它负责遍历表中的所有数据，并根据 过滤条件(如果有) 筛选出符合条件的元组。

Insert

向表中插入元组，需要更新与之相关的索引。

Update

先删除受到影响的元组(标记受到影响的元组的元信息标志位 is_deleted_ = true)，然后插入新的元组。(在 Project 3 中， update 不是原地更新)

Delete

标记元组为删除状态(is_deleted_ = true)，并删除与之相关的索引。

IndexScan: 索引扫描

  1. 点查询^[2]，如 SELECT FROM WHERE =
  2. 有序地检索：使用 B+Tree 索引在一张表中检索元组，批量返回。对于有 ORDER BY 的查询，通常会检查是否有索引。如果有索引，会走 索引扫描；否则，全表扫描后再排序。

    3. [^2]:优化器的优化规则: 将 SeqScan 顺序遍历 转化为 IndexScan 索引扫描

    Optimizing SeqScan to IndexScan

    1. 谓词下推: 在顺序扫描 SeqScan 执行器中实现 谓词过滤 逻辑，后续索引扫描也会复用这套过滤条件。(这部分在 BusTub 已经实现好了)
    2. 使用索引: 从谓词中检查过滤条件列，如果这一列存在索引，就会生成一个 IndexScanPlanNode。

    具体的执行逻辑:

    1. 优化器采用自底向上的优化策略，因此需要优先递归优化子节点。
    2. 检查当前节点类型
      │ ├─ 不是 SeqScan → 直接返回
      │ └─ 是 SeqScan → 继续
    3. 检查过滤条件: 只有存在 WHERE 子句时，才有可能使用索引。

    Task 2 聚合 & 联结执行器

    Aggregation

    对于 GROUP BY 子句，聚合执行器需要对每个 group 计算聚合函数。一种普遍的策略是使用 哈希表，将 GROUP BY 后紧跟的列值作为 哈希键 key。

    聚合执行器不需要处理 HAVING 条件，原因在于 Planner 在处理时，会在 Aggregation 上面生成一个 FilterPlanNode，也即先聚合执行计算，再执行过滤。

    聚合执行器需要处理 4 种情况，分别是:

    1. 没有 GROUP BY 但是有聚合表达式 select count(*) from t1;
    2. 有 GROUP BY 但是没有聚合表达式 select v1 from t1 group by v1;
    3. 既有 GROUP BY 又有聚合表达式 select v1, sum(v2) from t1 group by v1;
    4. 既没有 GROUP BY 又没有聚合表达式

    NestedLoopJoin

    嵌套循环联结

    这里我们主要实现的是 左外联结 和 内联结。
    关于 内联结: 左孩子返回一批 Tuples，我们需要对每一个 tuple 遍历右表, 然后判断是否满足谓词条件，若满足，则加入答案；
    关于 左外联结: 需要额外特判左孩子返回的 tuple 没有任何匹配的情况。

    时间复杂度: $O(n \times m)$

    NestedIndexJoin

    Planner 生成的原本是 NestedLoopJoin，当 Optimizer 发现 JOIN 后跟着的条件是 等值条件，且某一列上有索引时，就会将 NestedLoopJoin 转化为 NestedIndexJoin。

    Task 3 哈希联结执行器和优化

    当 JOIN 后面跟着多个等值条件时，才会用到该执行器。

    1. Build 构造哈希表: 选择行数更少的表，逐行扫描左表所有 tuple，提取等值条件作为 hash key；
    2. 逐行扫描右表每一条 tuple，与嵌套循环联结不同的是，右表的每个 tuple只会遍历一次，因此时间复杂度为 $O(n + m)$。

    这里我们只需要处理 AND 连接的情形。

    Optimizing NestedLoopJoin to HashJoin

    考虑当执行计划 Planner 给出的节点是 NestedLoopJoin 时，如何优化为 HashJoin。
    首先，提取等值条件；
    然后，根据等值条件，选择行数更少的表作为左表(理论上应该选择规模更小的表作为左表来构建哈希表，但是 BusTub 似乎并没有实现这一部分)

    Task 4 外部归并排序+Limit执行器+窗口函数

    当出现 ORDER BY 子句时，若 ORDER BY 后面跟着的列值是索引列，那么天然有序；否则需要生成 SortPlanNode 执行排序。

    外部归并排序的执行策略是:

    1. 排序阶段
      对于孩子节点的每一批 tuples，我们对其排序之后，将其写入页面；如此执行多次，形成多个有序的页面；
    2. 合并阶段
      将多个有序的页面，两两合并，不断缩小规模，直至整体有序。

    总结: 使用的是 归并排序 的思想，不过是 二路归并，工业实现常采用 多路归并。

    之所以叫做外部归并排序，是因为在排序过程中，需要不断将有序的数据写回磁盘。

    Limit 执行器就是输出前 k 条元组。

    窗口函数需要根据有无 PARTITION BY 和 有无 ORDER BY 划分为 4 种情况。
    BusTub 确保测试集如果有 ORDER BY，那么对于多个窗口函数来说，排序规则是一致的。所以对于有 ORDER BY 的情况，我们需要先进行排序；在这之后如果有 PARTITON BY，那么我们需要根据 PARTITON BY 后的列值分区构建哈希表。

    而在真实的数据库实现中，应该是先分区构建哈希表，然后再在每个分区内部独立排序。
