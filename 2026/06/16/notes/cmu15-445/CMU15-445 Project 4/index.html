并发控制

在 CMU15-445 的最后一个Project中，你需要实现 optimistic multi-version concurrency control (基于乐观校验的多版本并发控制)^[1]
[^1]: InnoDB 实现的是 悲观 MVCC

Task 1 时间戳

在 Bustub 中，每个事务都被分配两个时间戳：读时间戳和提交时间戳。在该任务中，你需要在 transaction manager 中实现时间戳的正确分配。

1.1 时间帧分配

当一个事务开始时，分配一个读时间戳，这个时间戳等同于 transaction manager 中最近一次事务的提交时间戳。
读时间戳意味着该事务开始时所能看到的版本。
当一个事务提交时，它会更新自己的提交时间戳。
在具体的实现中，该事务的提交时间戳 = transaction manager 中最近一次提交事务的时间戳 + 1。
注意：

  1. 首先，transaction manager 中用于记录上一次提交事务时间戳这个变量它是 原子 的。
  2. 其次，这个变量是单调递增的，因此具有唯一性。我们可以通过这个唯一提交的时间戳来辨别究竟是哪个事务做出的修改。

1.2 Watermark(水位线)

Watermark 是所有还没有提交或者中止的事务的读时间戳的最小值。
如果没有事务，那么 Watermark 就是最近的提交时间戳。
计算 Watermark 最简单的方法是: 在 transaction manager’s map 中遍历，找到所有正在进行的事务的读时间帧，取最小值。
然而，这样的时间复杂度是 $O(n)$ 的。
在这个任务中，你需要实现一个时间复杂度至少为 $O(logn)$ 的算法来计算 Watermark 才能通过测试。

在这里，我简单记录一下我的实现。

我是使用了 unordered_map，其中 key 是事务的读时间戳，value用于计数。然后用 set 来维护 unordered_map 中出现至少 1 次的 key，这样每次启动新的事务时，我们只需要 $O(1)$ 的时间复杂度来更新 Watermark。但是这样做的话，在移除事务时，若是被移除事务的读时间戳刚好是最小的，且 value计数值减为0时，我们就需要把 set 中对应的元素给擦除掉，更新 Watermark，因此移除事务的平均时间复杂度是 $O(logn)$的。

经过同学的提醒，我觉得这里可以直接用 map，这样每次更新最小值是$O(1)$的，插入/删除维护红黑树是$O(logn)$的。已修正。

Task 2 存储形式和顺序遍历

BusTub 将事务信息存储在

  1. table heap(表堆)
  2. transaction manager(事务管理者的工作区)
  3. each transaction

table heap 总是可以访问 page，用 page guard 访问最新的 tuple meta、tuple data。

transaction manager 存储了一个指针，指向每个页面上 tuple 最新的 undo link (如果有的话)。

通过 undo link 我们可以找到其对应的 undo log。
transaction 存储他们所创建的 undo logs，其中每个 undo log 用 标志位 记录是否对这一列做出了修改，如果做出了修改，那么修改前的值是什么。

2.1 Tuple Reconstruction

2.2 Sequential Scan

在这个任务中，你需要重写 Project 3 实现的 Sequential Scan executor。
对于你从 table heap 中检索出来的每一行 tuple，他们都是最新的。你需要根据 tuple meta 的时间帧来判断这一行 tuple 对当前事务是否可见。
如果不可见，就需要检索 undo logs， 重建 past tuple version。

你需要在 execution_common.cpp 中实现 CollectUndoLogs 函数，该函数根据一个事务的读时间戳，返回所有你需要的 undo log。
针对当前事务的读时间戳，你需要处理以下三种情况:

  1. tuple meta .ts_ <= read_ts，这种情况下不需要回滚。
  2. tuple 被另一个事务修改过但是还没有提交，或者说这一行 tuple meta.ts_ > read_ts
  3. tuple 被当前事务修改过

BusTub 用一个 int64_t 的 timestamp 同时表示 提交时间戳和事务ID。
核心思想: 利用 64 位整数的次高位作为标记位（tag），区分这个 timestamp 到底是已提交事务的提交时间戳，还是未提交事务产生的临时时间戳。
简而言之, 一个有效的提交时间戳是 [0, TXN_START_ID - 1]，其中 TXN_START_ID = 1 << 62。
当一个时间戳与 TXN_START_ID 进行 & 位运算的结果是 1，那么就以为这个这个时间戳是一个未提交事务生成的临时时间戳: TXN_START_ID + 事务ID = 临时时间戳。

为什么用次高位做标记？
因为对于 int64_t 而言，最高位 = 符号位。如果一个未提交事务生成的临时时间戳是一个负数，显然不符合我们的直觉。

如何区分一个 tuple 的时间戳是已经提交事务修改的，还是未提交事务修改的？
已提交事务的时间戳是一个 [0, TXN_START_ID - 1] 之间的整数。

若当前 tuple 的时间戳不为当前事务可见，那么需要收集 Undo logs，也即沿版本链回溯，找到第一个对当前读快照可见的版本。

seq scan 是快照读，顺着 undo 版本链找到旧版本。

Task 3 MVCC

3.1 Insert Executor

新插入的 tuple 的时间戳应该被设置为当前事务的临时时间戳。
你需要通过 AppendWriteSet 函数将这个 RID 加入到该事务的 write set 集合中。

已经提供了 table_heap::UpdateTupleInPlace 和 transaction manager::UpdateUndoLink 两个函数，用于更新 tuple 和 undo link，这些函数 模拟 原子操作，你需要提供一个 check 函数，用于检测写冲突(多线程下存在多个并发事务更新 tuple 和 tuple meta。

3.2 Commit

同一时刻只有一个事务能够执行 Commit 函数。

事务在提交时，需要更新自己的提交时间戳。
然后遍历写集合，更新写集合中 rid 对应的 tuple meta 为该事务的提交时间戳。

3.3 Generate Undo Log

假设一个事务更新了某行 tuple 多次，我们期望对于一个事务而言，对同一个 tuple 行的所有更新操作，最终只产生一个 undo log。
对于每个 tuple 行的第一次修改会调用 GenerateNewUndoLog 函数，之后再次修改应该调用 GenerateUpdateUndoLog 函数来合并修改操作。

需要考虑以下三种情况:

  1. Update: 基于 base_tuple 和 target_tuple 生成一个 undo log，如果这不是该事务的第一次更新操作，那么请通过 GenerateUpdateUndoLog 函数来合并更新操作。
    对于每一个 rid，一个事务应该至多保存一个关于这个 rid 的 undo log。
  2. Delete: 你需要在 undo log 中暂存整个 tuple，这样这个 tuple 才能正常回滚。
  3. 插入: 对于插入操作，不会产生 undo log。

3.4 Update & Delete Executor

在更新或者删除一行 tuple 之前，你需要检查 写冲突。下面是你需要注意的情况:

  1. 如果一行 tuple 被一个未提交的事务修改，那么其他事务不能修改它。如果其他事务想要修改，那么就造成了写冲突， 检测到写冲突的这个事务所做的所有修改应该被丢弃。
  2. 当一个事务 A 删除了一行并提交，另一个早于事务 A 之前的事务 B 在事务 A 提交之后也做了相同的操作。 事务 B 应该检测到写冲突。
    当检测到写冲突时，事务的状态应该被标记为 TAINTED，而且为了表示这条 SQL 语句执行失败，你需要抛出异常。

写冲突: 两个并发的事务对同一行执行写操作，存在修改版本覆盖风险。
如何检测写冲突: 孩子执行器 seq scan 是快照读，返回的是当前事务应该可见的版本，但是 update/ delete 写者是当前读，直接读取最新的版本。如果 update/delete 发现最新版本不可见，说明这一行数据已经被其他事务修改，写者应该能够检测出写冲突。

检测出写冲突的事务会发生什么？
事务的状态变脏，事务作出的所有修改会被丢弃。

3.5 垃圾回收

为什么需要进行垃圾回收？
MVCC会产生很多历史版本，当一个旧版本不会再被任何事务使用时就是垃圾，不回收的话这些垃圾会一直占用内存。

只有当所有的事务都停止时，才会开始垃圾回收。

在这个 task 中，你需实现一个简单的垃圾回收策略: 回收不再使用的事务。
这些事务的特点是: 它所记录的 undo log 对于具有最小读时间戳的事务都不可见。

water mark 记录了当前活跃事务中最小的读时间戳。
我们需要在 transaction manager 中遍历 transaction，如果一个事务的状态是已提交或者被放弃，那么这个事务可能是可以被回收的。
然后，遍历所有表中的每个 tuple 行，根据 tuple meta 和 water mark 的大小进行判断

  • tuple meta <= water mark 那么这个版本对所有活跃的事务都可见，我们不再需要他的版本链
  • tuple meta > water mark 当最新的版本不可见时，如果这一行存在版本链，那么我们应该找到 water mark 可见的第1个版本，截断版本链

==只要一个事务的 undo log 仍然被 water mark 可见(被当前活跃事务的最小读时间戳可见)，那么就有可能用到这个 undo log，就不应该被当做垃圾回收。==

3.6 放弃

在开始这个任务之前，所有检测到写冲突的事务都会变脏。
当变脏的事务放弃修改 tuple 时，其他活跃的事务就可以继续修改 tuple。

4.4 事务的串行化验证

为什么需要隔离级别？
在没有隔离级别的情况下，并发事务读写同一份数据会出现以下三种经典问题:

  1. 脏读: 读到其他事务未提交的修改
    txn A 更新一行，txn B 读到了 A 的修改，A 随后 abort，txn B 读到的是无效的脏数据。
  2. 不可重复读: 同一事务中两次读同一行得到不同结果
    txn B 读了一行值为 5，txn A 修改并提交该行为 10，B 再读得到 10，两次结果不一致
  3. 幻读: 同一事务中两次范围查询得到不同结果
    txn B WHERE a=1 得到 2 行，txn A 插入/修改更多行并提交，B 再查得到 5 行

各种隔离级别是如何解决这些问题的？

  1. 读未提交
  2. 读已提交
  3. 可重复读
  4. 事务的串行化

快照隔离
事务开始时，系统给予你一个该时刻的快照。
读：永远读「事务开始时」已提交的版本。即使其他事务在此期间修改了、提交了，完全不管，读的是老版本。
写：读最新的版本，先检查写冲突^[2]，然后再在真正获取写锁之后，验证该行的时间戳是否仍与事务开始读时一致，如果不一致，说明中间有其他事务先修改了这一行，所以事务的状态应该变脏，放弃所有修改。

Compare-And-Swap (CAS)
本是 CPU 提供的一条 原子指令，它做的事情是:
我觉得内存里这个值是 A，如果真是 A，就把它改成 B；否则，告诉我失败了。

Bustub 中的 check 函数就是数据库层面的 CAS：通过在写锁保护下比较时间戳是否仍为期望值，来决定本次写入是否安全——这就是乐观并发控制的核心思想。

避免了:

  1. 脏读: 你读到的是已提交版本，不会读到未提交内容
  2. 不可重复读: 两次读同一行，永远基于同一个快照，结果一致

==快照隔离从现象上避免了幻读的出现，但是它不能保证事务的可串行化。==

什么是事务的可串行化?
多个事务并发执行的最终结果，必须等价于某种串行执行顺序。幻读并不是串行化想要解决的问题。串行化是保证 并发执行的最终结果等价于某种执行顺序。

例子：
txn2: 把所有 a=1 的行改成 a=0
txn3: 把所有 a=0 的行改成 a=1

如果串行执行（先 txn2 后 txn3）：
txn2 执行后 → 全变成 a=0
txn3 执行后 → 全变成 a=1
最终：全是 a=1

如果串行执行（先 txn3 后 txn2）：
txn3 执行后 → 全变成 a=1
txn2 执行后 → 全变成 a=0
最终：全是 a=0

快照隔离下并发执行：
txn2 改了它能看到的 a=1 的行
txn3 改了它能看到的 a=0 的行
最终：一半 a=0，一半 a=1

↑ 这个结果在任何串行执行中都不可能出现！
所以它是不可串行化的。

快照隔离只检测: 两个事务有没有写同一行。

如何实现可串行化?事务的串行化校验？
在 BusTub 中，为了进行串行化校验，你需要实现 乐观后向校验。

当调用 sequential scan executor 或者 index scan executor 时，你需要存储 the scan filter(谓词)，同时正确地追踪一个事务的写集合。

  1. 你不需要对一个只读的事务进行校验
  2. 收集所有已提交的事务(这些事务的提交时间戳 > 当前事务的读时间戳)
  3. 收集被这些事务修改的 rid
  4. 当 rid 对应的最新版本对当前事务不可见时
  • 对于 insert，tuple 是没有版本链的，如果这一行满足谓词条件，那么事务所做的修改都应该被放弃
  • 对于 delete, 如果被删除的 tuple 满足谓词条件，那么事务所做的修改都应该被放弃
  • 边界情况: 一个事务新插入一行之后又将该行删除，这不应该被视作 delete
  • 对于 update，你应该检查快照可见的版本与最新的版本……
