3.1 简单介绍一下你的 BusTub / CMU 15-445 项目

Bustub 是 CMU 15-445 以教学为导向的关系型数据库，面向磁盘，整体架构基于火山迭代模型。

我主要实现了一些模块。

首先是缓冲池部分，因为数据库的数据都存储在磁盘上，而磁盘 IO 是比较慢的，所以缓冲池主要负责将磁盘上固定大小的页面（8KB）缓存在内存里。

为了尽可能地减少磁盘 IO，我们自然而然更希望那些被频繁访问的页面能够保留在缓冲池中，这就是页面置换算法的作用。

然后是 B+Tree，这是我认为整个实验过程中最棘手的一部分，难点在于并发控制。

在这一部分，为了提高并发效率，我接触到一种锁耦合协议（latch crabbing）。而且针对删除操作可能导致频繁节点合并的问题，通过引入懒删除机制，可以进一步减少 B+ 树结构的调整开销。

关于执行器，每个执行算子都需要实现一个 Next() 接口，数据自底向上返回，工作过程类似于火山喷发。

其中让我印象比较深刻的是外部归并排序，它主要针对的是数据量超过内存的场景，这种情况下，没法将所有的数据一次性加载进内存，一种处理的思想是分批处理，得到多个有序的数据段，然后再进行归并。

最后是事务部分，我实现了基于快照隔离的 MVCC，通过时间戳机制控制数据的可见性。

通过这个项目，我大致了解了一条 SQL 语句的执行流程，并且对数据库这个方向产生了浓厚的兴趣。

3.1.1(延伸): 讲一下大概的执行流程(架构)？

bustub 是一个以教学为导向的关系型数据库，面向磁盘， 整体架构基于火山迭代(volcano)模型。

具体而言，大致可以分为以下四个部分，分别是:

  1. 查询处理
  2. 查询执行
  3. 并发控制
  4. 存储

每个部分又可以接着细分为一些小的模块。
例如，在查询处理层，一条SQL语句输入进来，会先后经过语法解析器和绑定器，生成一棵用于表示查询的抽象语法树。

绑定器将 * 转化为实际的列。

然后，根据这棵语法树生成查询计划。优化器会检查查询计划，并对其进行优化。

查询执行方面，执行引擎根据计划树，自上往下递归，创建节点对应的执行器。所有执行器都实现了统一的初始化和迭代接口。执行引擎通过根执行器反复调用next()接口获取查询结果。

并发控制方面，主要涉及到事务管理，
再往下就是存储，像缓冲池就是存储层面的东西。

3.2 讲一下缓冲池这部分你主要做了什么工作？

关于页面置换算法，我实现的是ARC。

传统的LRU会有这样一个问题：

  1. 预读失效
  2. 缓冲池污染

根据程序的空间局部性原理，一个页面被访问，那么它附近的页面可能很快也被访问。因为，为了尽可能地减少磁盘 io，我们通常会做这样一种预读的工作。但是，很有可能这些被预读的页面实际上并没有被访问，这是预读失效。

而且，在 lru 中，一次预读的工作通常会带进来大量的一次性页面，导致真正的热点页面会挤出缓存，导致缓冲池污染。

ARC因为他维护了4条链表，mru(最近被访问一次)、mfu(最近被访问多次)，以及各自对应的幽灵链表，所以它能够避免这个问题。

ARC只负责淘汰页面，能不能淘汰这个页面是由缓冲池管理说了算。具体而言，缓冲池管理负责维护一些空闲的页框。页框就是一个由元数据和页面构成的类，其中元数据包括页号、脏位、原子变量pin_count。

原子变量pin_count不为零时说明还有其他线程正在读写这个页面，不能被淘汰。脏位决定这个页面被淘汰时需不需要写回。如果需要写回呢，缓冲池管理就会通过消息队列发起一个写请求。(这部分是一个多生产者-单消费者模型)。由后台线程负责执行磁盘IO。

磁盘IO执行完毕之后由后台线程通知生产者(这里是异步执行，同步阻塞)。

这里用到了C++的future，我的理解是bpm将task给消息队列，然后调用future.get()。

异步 vs 同步

异步: 调用者发起请求后，不需要等待，结果完成后由别人通知我
同步: 调用者发起请求后，需要等待执行的结果

阻塞 vs 非阻塞

阻塞: 调用者发起请求后，如果结果没准备好，调用线程会等待，等待期间线程不能做别的事，通常线程会被挂起。
非阻塞: 调用者发起请求后，如果结果没有准备好，立即返回，线程可以继续做别的事

我觉得下面这段话还是不要说比较好。

这里我遇到一个问题，我还挺有印象的，就是一个脏页被驱逐前需要先持有bpm大锁擦除页表，然后放掉大锁落盘。

但是另一个线程认为页表中已经没有映射，这个页面不在内存中，于是加载了磁盘上的旧版本，出现数据不一致的情况。

针对这个问题呢，我加了一个unordered_set，用于标记正在进行磁盘IO的页面集合，同时用一个条件变量。当这个页面被加载进内存或者写回之后，就通知一下其他线程。这个条件变量绑定的是bpm大锁。

当然这里也有不同的做法。比如说我一个同学它是给页表(页号和页框状态的映射)页框状态加了一个状态机，然后它也用到了条件变量，不过这个条件变量绑定的是页框的读写锁。

仔细想了想，我觉得我的这种做法虽然简单，但是并发度高的情况下，锁冲突可能比较严重吧。

3.2.1(延伸) LRU-K是不是也能解决缓冲池污染这个问题呢？所以他们有什么区别呢？

像刚才提到的LRU，它的问题就是扫描污染；

相应地，LFU虽然对稳定热点友好，但是假设一个热点很久不再被访问，但是由于其历史访问频率太高，这个页面也可能很难被淘汰掉；

再说LRU-K，它的思想是：比较每个页面倒数第K次访问时间，谁的第K次访问最早，谁就先被淘汰。这样的话，假如说K=2，那么那些实际上没有被访问的预读页面还没有成为热点页面就会被淘汰掉，所以它确实也可以解决这个问题。

ARC和LRU-K的区别在于，LRU-K的这个K是固定的，K取得太大，维护的成本会变高；K取得太小，又可能不够区分热点数据。

而ARC的好处就在于它的自适应性，就是它可以根据一个参数来动态调整最近被访问一次页面(冷启动页面)和最近被访问多次(热点页面)的比例。

怎么调整呢？简单举个例子。

假如一个冷启动页面被淘汰了，现在我们还想访问它，这就说明它原本有机会成为热点页面，我们把它淘汰得太早了。于是 ARC 做两件事：一是把这个页面重新加载进来，放进 mfu 链表；二是增大 mru 链表的目标大小，给冷启动页面更多缓存空间，避免下次又过早淘汰。

LRU: 谁最长时间没被访问，淘汰谁
LFU: 谁历史访问次数最少，淘汰谁
LRU-K: 比较每个页面倒数第K次访问时间，谁的第K次访问最早，淘汰谁

3.3 并发控制这块你是怎么做的？

在缓冲池中，为了支持并发访问，我的实现是首先确认一个大的前提：保证一个页面在内存中只会有一个版本。

这部分是怎么保证的呢？

就是说缓冲池有一把大锁，主要用于保护页表(unordered_map），和正在加载的页面(unordered_set)，以及还有哪些空闲的页框(双向链表)。
页表是页号和页框号的映射，数据结构是哈希表。
页框，它由一些元数据，如脏位、页号、页框号、读写锁+缓冲区构成。

正在加载的页面集合，主要记录的是页号，数据结构也是哈希表。

判断一个页面是否在内存中，就看哈希表中是否存在页号：页框号这样的映射。
判断这个页面是否已经有别的线程正在加载了，就看正在加载的页面集合，是否存在这样的页号。

除此之外，为了确保一个页面在驱逐之前，判断是否还有线程在访问它，每个页框都维护了一个原子变量叫 pin_count_。只要有个线程在访问它，那么这个原子变量就>0，我们不允许驱逐这样的页面。

这是缓冲池方面的并发控制。

那 arc 呢，它有自己的锁，这个锁主要保护的是四条链表，和两个哈希表。

mru
mfu
mru_ghost
mfu_ghost

哈希表主要维护的是页号或者说页框号与页框状态的映射。
页框的状态主要记录了页号、页框号、还有在哪条链表中(枚举)、以及指向这个元素的迭代器。

3.4 说一下B+Tree的并发控制吧？搜索、插入/删除。

在实现B+Tree的过程中，我使用了锁耦合机制。

具体而言，搜索时自上而下拿读锁，先拿父节点读锁，再拿子节点读锁，在这之后释放父节点读锁，一路向下。

这是为了兼顾安全和效率。减少持锁有利于提高并发度。

写操作包括插入和删除键值对，有乐观和悲观两条路径。

这里我就以插入的过程简单说明一下。

乐观路径像搜索一样下行拿读锁，到叶子节点时直接拿写锁。

这里为什么要直接拿写锁呢？原因是在实现这部分的过程中，我踩过坑。

因为它这里它没有原子的锁升级机制，所以要修改页面，必须先释放读锁再拿写锁。而我们最开始走乐观路径，是假设本次插入不会导致节点的分裂。但是在我们放弃读锁，等待写锁的这个过程中有个锁窗口，这就导致我们在读锁下判断是安全的，但是再拿到写锁，我们会发现这个叶子结点的页面上的键值对已经满了。

这时如果再插入一个节点就要触发叶子节点的分裂，分裂会有一个自下而上的写传播过程。而乐观路径不知道父节点是谁，所以这时只能放弃叶子结点的写锁，重新走悲观路径。

悲观路径就是沿着父节点向下一直拿写锁。释放锁的时机就是当我们确定父节点的索引已经更新了，这时我们才可以释放孩子节点的锁。

3.4.1 墓碑机制怎么做的？

墓碑机制就是删除操作不立即进行物理删除，而是在逻辑上将其标记为墓碑。这个意思就是说，墓碑缓冲区是固定大小的，它存储的是kv的索引下标。

物理删除时需要移动元素，这个操作的时间复杂度是O(n)的，而标记墓碑只是O(1)。当墓碑缓冲区满时，才通过驱逐最老的墓碑来腾出空间。这是一种懒删除策略。

同时，如果同一个键被删除后又重新插入，可以直接复用该位置，避免重新分配。

墓碑的本质是一个先入先出队列。

3.4.2 你就说一下这个删除逻辑是怎么做的？

删除路径的话，首先走的是乐观删除这条路。
这条路指的就是自上而下搜索，我们需要先判断这次删除是不是安全的。安全的意思就是此次删除不会导致当前这个节点产生下溢。

B+树它为了维护它的结构，要求每个节点上的键值对要处于一个范围内。
少了就合并，多了就分裂。

如果说不会下溢的话，就先查一下缓冲区，判断一下是不是已经是墓碑，如果是的话，直接返回就可以了。如果不是，那就将其标记为墓碑，追加到墓碑缓冲区。

如果说墓碑缓冲区满了，这时才会执行真正的删除逻辑，包括删除键值对，更新缓冲区中的索引值。

这是安全条件下的删除。
如果说不安全的话，就说明本次删除可能会导致叶子节点的合并，这时需要自上而下拿写锁重做，走悲观路径。

大致的删除逻辑和刚才说的差不多是一致的。

但是这里的话，如果说执行真正的删除操作之后，一个叶子节点它发生了下溢，那么它需要问它的父节点，我有没有左右兄弟，我要向他们借 key。

因为是懒删除，所以借key，也可能借的是个墓碑。如果借到的是个墓碑呢？那就让对方把这个墓碑给扔了(代码里写的是覆盖操作，所以也算是删除了)，然后当前节点将要删除的这个位置标记为墓碑，执行完毕。

那如果它的左右兄弟都借不了，它才会选择和左右兄弟进行合并，合并的时候可能会发生墓碑缓冲区上溢，这个时候也会把多余的墓碑给扔掉。

3.5.2 seqscan 和 indexscan 有什么区别？

二者的主要区别在于获取数据的方式不同。

seqscan 是遍历表中的数据，逐行检查谓词条件，它的时间复杂度是O(n)，最坏情况下需要遍历整张表；

indexscan 是如果谓词条件上的列名有索引，且谓词条件是等值条件，就可以通过索引找到符合条件的行。

  • 在B+树中进行查找id，时间复杂度为O(logn)(B+树的高度)
  • 根据索引项中的记录来找到这行数据位于哪个数据页的哪一行。

这里可能会涉及到一个回表的过程(如果id是主键索引，叶子节点存储的就是完整的行数据；非主键索引需要回表。

3.5.3 seqscan 怎么实现的？

seqscan 是顺序扫描执行器，用于逐条遍历表中的记录，并根据查询条件过滤出符合要求的记录。

在 volcano 执行模型中，每个执行器都实现了 init() 和 next() 两个接口。
在 init() 接口中，seqscan 负责获取目标表的 schema，初始化扫描迭代器。
每次调用 next() 接口，seqscan要么吐出一些行数据，要么返回一个没有数据的标志位。
一般情况下，seqscan会根据谓词条件进行过滤；
若是在快照隔离机制下，seqscan在读取每一行时还要结合这一行的时间戳和标志位来判断可见性，不可见就沿着undo log 版本链回溯旧版本。

3.5.4 aggregation 聚合怎么做的

聚合执行器在 init() 接口中会初始化一张哈希表和用于遍历这张哈希表的迭代器，这张哈希表通常是对 group by 子句后面跟着的列名对应的值，做哈希。

注意：聚合和核心标志是聚合函数，聚合不一定有 group by 子句。

3.5.5 nested_loop_join、nested_index_loop_join、 hash_join 有什么区别？

nested_loop_join 是嵌套循环连接，
一般来说是遍历小表(外层表)的每一行，在大表中根据联结条件来找匹配的项，这个时间复杂度是O(m*n)的。
nested_index_loop_join和前者的主要区别在于，联结条件的内层表有索引。遍历小表的每一行，大表走索引。
hash_join大概分为两个阶段:

  1. 构建阶段：根据联结条件对小表对应列的值做哈希，value是行数据；
  2. 探测阶段：遍历右表，只遍历一遍，同样是对大表对应列的值做哈希，进行条件匹配，时间复杂度是O(m + n)

在什么情况下，nested_loop_join 会转化为 hash_join？
联结条件是等值条件。

自联结，内联结，左外联结、右外联结。
自联结：一张表做两张表用
内联结：先做笛卡尔积，再根据联结条件过滤
左外联结：左表的每一行都输出，右表匹配不上是填null

3.6.3 时间戳是怎么分配的？(快手问过)

在事务开始时分配一个读时间戳，这个读时间戳一般是上一个已提交事务的提交时间戳。

3.6.4 快照隔离怎么实现的？

很容易理解，每个事务开始时通过时间戳，从磁盘读取期望的页面，然后检查每一行的metadata。
metadata就是时间戳和墓碑标记。
先看时间戳，如果不可见，就需要沿着undoLog版本链回溯到可见的版本。

快照隔离的好处是读写互不阻塞。
像 select 就是快照读；
而 update、delete 是原地写，他们需要检查写写冲突：
一行 tuple 的时间戳标记对我来说不可见，就说明已经有别的事务作出了修改，后来的写者应该放弃修改。

写写冲突的校验包括两层：

  1. 预检：检查刚读到的每一行对我快说是否可见，这一步是确定我的快照依然有效；
  2. 写回之前：进行cas校验，持页锁校验刚才读到的时间戳和现在页锁下保护读的时间戳是否还一样

3.6.5 可串行化怎么保证？

每个事务负责维护读写集合。
只读事务不需要校验。

写事务在提交前，收集他读快照之后已经提交事务的写集合，根据谓词条件来校验是否发生冲突。
比如说

T1 快照时刻：balance=50，满足 balance>=20  → old_match = true
   （T1 据此决定"可以转账"，并开始做它的写操作）
        ↓ 时间流逝
T2 提交：把 id=1 的 balance 改成 10（它自己扣了款的）
   → 最新版 balance=10，不满足 balance>=20  → new_match = false

T1 提交前 VerifyTxn：old_match(true) vs new_match(false) → 冲突！回滚 T1

在面对一个问题时，如果能用一台计算机解决，就没有必要设计分布式系统。事实上，很多工作都可以用一台计算机来完成。那么，为什么需要分布式系统呢？ 人们期望获得更高的计算性能。大量的计算机意味着大量的并行运算。 可以提供容错。如果两台计算机都在运行相同的任务，一台计算机失败了，另一台计算机可以继续运行。 一些问题天然是分布式的。如银行转账系统。 基础架构 存储 通信(网络) 计算 构建分布式系统的目的 可扩展性。比如我用一台计算机解决了一些问题，当我有两台计算机的时候，我期望可以花费一半的时间就能够解决相同的问题。这在现实中很难实现。 可靠性(容错)。比如，你构建了一个有两个拷贝的多副本系统。...
