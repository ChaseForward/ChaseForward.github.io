前言

面向磁盘的数据库管理系统(DBMS, database management system)，BusTub。

首先，面向磁盘意味着DBMS的存储位置是永久存储。
第1个编程任务是实现缓冲池管理。

Q1: 为什么需要缓冲池管理(buffer pool manager)?
面向磁盘意味着数据库的数据最终都会落盘。如果每次查询、更新都直接访问磁盘，数据库的性能会非常低。因为磁盘IO很慢。
因此呢，一般来说，数据库会自己维护一个缓冲池，将最近访问或者频繁访问的页面缓存到内存中。当访问一个页面的时候，缓冲池管理首先检查它是不是还在内存中，如果存在，就直接从内存中读取；如果不在，才会做磁盘IO。

除了缓存页面之外，缓冲池管理还负责页面的分配与淘汰、页表的维护，以及脏页的写回等等。

一个页面的大小是 8KB。
页面是固定大小的。

Q2：page 和 frame 的区别在于？
缓冲池管理将这些 page 存储进固定大小的缓冲区(frame)

Task 1 Adaptive Replacement Cache(ARC) Replacement Policy

页面置换算法负责追踪缓冲池中的页面，以决定哪个 frame 中的 page 应该驱逐出内存，落盘。

Q3: 解释一下 ARC？

LRU 的缺点在于缓冲池污染。
具体而言，在批量扫描数据的场景中，许多页面只会被访问一次，但是这些被访问一次的页面会占据链表的前排位置，最终导致被淘汰的页面，很有可能是被频繁访问的热点页面，这就是缓冲池污染。

与LRU相比，ARC 是一种自适应性页面置换算法。由于它的自适应性，它的表现要普遍优于 LRU。
ARC 负责维护两个缓存链表，一条链表维护最近被访问过一次的页面，另一条链表维护被频繁访问多次的页面。

在上述的场景中，因为ARC维护了两条链表，所以那些仅仅被访问过一次的页面不会影响被访问多次的热点数据。

而且ARC的自适应性也使得它能够根据当前的工作负载来动态调整两个缓存链表的比例。例如，在批量扫描数据时，它会允许最近被访问一次的链表维护更多的页面。

除此之外，还有两条对应的幽灵链表，负责追踪最近被驱逐的页面。

这个组件负责处理读写操作。它会维持一个后台的工作线程负责处理读写请求。这里用到了消息队列。
这个队列是基于mutex+condition variable实现的。

在目前的实现中，一个线程绑定一个队列，I/O 串行执行。
这部分可以优化的点在于，把串行 I/O 改成并行 I/O，让不同页面的 IO 可以并行处理，同时保证同页请求顺序执行。

为什么要使用读写锁？

因为在对数据库进行增删改查时，读写锁非常适合这种能够明确区分读写的场景。读锁可以共享，写锁只能独占。

原子变量 pin_count_ 有什么用？

因为使用了读写锁，所以我们可以通过原子变量 pin_count_ 是否为0来判断当前是否有线程正在读/写该页面。当驱逐页面时，必须要选择 pin_count_ == 0的页面。

脏页标记？

然后释放 bpm 锁，拿到 frame 的读/写锁。
