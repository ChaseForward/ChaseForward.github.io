6.5840 distributed system

Lab 4 Key/Value Server

在这个实验中, 你将基于 Lab 3 中的 Raft 协议, 实现一个 fault-tolerant key/value storage service(具备容错能力的存储服务)。该服务包含多个节点的服务器, 这些服务器基于 Raft 协议来保持一致性。即便存在网络分区或者其他失败, 只要过半的服务器还活着而且可以互相通信, 那么你的服务就可以持续处理来自 client 的请求。

client 通过 clerk(代理) 与你的 Key/Value service 进行交互, 就像 Lab 2 那样。

线性一致对于单一服务器而言相对来说比较容易实现。但是在面对并发的请求时, 多个 server 如何对外表现地看起来就像是单一服务器那样对外提供服务?

这个实验包括 3 个部分。
在 Part A: 你将基于 Lab 3 中的 Raft 协议, 实现一个复制状态机。replicated-state machine(rsm) 并不关心实际的请求是什么, 它只负责把这个请求转发给 server。
在 Part B: 你将使用 rsm 实现一个 replicated key/value service。
在 Part C: 你将会用到 你在 Lab 3D 实现的快照。

Part A: replicated state machine(rsm)

在一个 client 与 基于 raft 的 server 集群进行交互的普遍场景中, 存储 service 与 raft 有两种交互方式:

  1. leader 通过调用 raft.start() 将 client 的请求当做一条日志暂存, 然后所有的 follower/candidate 会收到这条日志。 在 raft 协议中，当这条日志被复制到多数节点之后, leader 就认为这条日志可以提交了。提交的意思就是 raft 能够保证这条日志会被集群中所有的机器所执行。
    注意: leader 认为可以提交, 并不意味着这条日志已经被执行。这也是 commitIndex 和 lastApplied 的主要区别。
    lastApplied 表示 leader 已经执行了的最后一个日志的索引。而每一个需要执行的日志都会通过通道发给 rsm。

rsm 扮演的角色类似于 service 和 raft 之间的中介。

一个正常的执行流程是:

  1. client 给 充当 leader 的 server 发送请求
  2. server 通过调用 rsm.submit() 方法将这个请求原封不动的转发给 raft
  3. raft 继续调用 rf.start() 方法将这个请求当做一条日志，赋值给多数 server
  4. rsm 会在 submit() 方法中等待执行的结果
