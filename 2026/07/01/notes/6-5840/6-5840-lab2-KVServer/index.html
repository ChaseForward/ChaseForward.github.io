6.5840 distributed system

在不可靠的通信环境下(网络可能丢包、乱序、延迟)，在单机上实现一个 Key/Value Server，需要保证两个核心语义:

  1. Put 操作至多执行一次(exactly-once / at-most-once)
  2. 所有操作满足线性一致性(linearizable)

系统架构

角色与交互

每个客户端通过 Clerk(客户端库)与 KV Server 交互:
应用程序 → Clerk → (RPC) → KV Server

Clerk 的职责(对应用透明):

  • 封装 RPC 的网络调用细节
  • 处理网络失败时的重试逻辑
  • 对 reply.Err 进行分类处理

Clerk 向应用暴露的接口:

  • Get(key) → 返回 (value, version, err)
  • Put(key, value, version) → 返回 err

RPC 接口

Client 向 Server 发送两种 RPC：

操作 含义
Put(key, value, version) 写操作
Get(key) 读操作

Server 端数据结构

Server 在内存中维护映射:
key -> (value,version)

  • value：键当前的值
  • version：该键被成功写入的次数

示例：Client 发起 Put(new_key, new_value, 0)，Server 存储为 new_key → (new_value, 1)，表示该键被写入了 1 次。

问题一：如何确保 Put 至多执行一次？

用 版本号做幂等检查。

幂等: 多次执行的结果和单次执行一模一样，不会产生额外副作用。

Server 端的每个 key 在维护 value 的同时，也会维护一个 version number(版本号)。

client 端的 Put 请求必须携带版本号。

Server 只有在 client 请求的版本号与当前版本号匹配时，才会执行更新，然后版本号也更新。这样一来，同一个 version的请求最多成功一次。

背景

网络不可靠，客户端可能会重传同一个 Put 请求:

  • 请求丢失：客户端没收到回复，重发
  • 回复丢失：Server 已处理，但客户端没收到回复，重发

如果不加处理，同一个 Put 可能被执行多次，破坏语义。

方案: 基于版本号的幂等检查

核心思想：为每个 key 维护一个 version，Put 请求必须携带期望的版本号。

处理流程:

  1. Server 收到 Put(key, value, expected_version)
  2. 检查: Server 端该 key 的当前 version 是否等于 expected_version
  3. 匹配: 执行写入，version 自增 +1，返回 success
  4. 不匹配: 拒绝写入，返回 version mismatch

版本号如何保证至多一次？

Server 状态：x → (value=5, version=2)

Client A: Put(x, 10, version=2) ← 期望版本为 2 → Server 检查: 2 == 2，匹配！ → 更新为 x → (value=10, version=3) → 返回 success

Client A (重传): Put(x, 10, version=2) ← 仍然期望版本为 2 → Server 检查：3 ≠ 2，不匹配！ → 返回版本不匹配

结论：由于 version 具有唯一性，基于同一个 version 的更新最多成功一次。

客户端如何判断结果？

场景 客户端收到的回复 含义
第 1 次 RPC 正常返回 success success 明确成功 ✓
第 1 次 RPC 正常返回 version mismatch mismatch 明确失败 ✗
请求或回复丢失，客户端重传后收到 success success 明确成功 ✓
请求或回复丢失，客户端重传后收到 mismatch mismatch 不确定（可能之前已经成功过，也可能被其他人抢先更新）

客户端重传时如果收到 version mismatch，无法区分”已经成功过”和”被他人抢先”，但这没关系——Put 的语义保证了至多执行一次，而不是让客户端精确知道是哪一次请求成功的。

问题二：线性一致性解决什么问题？

在并发 + 不可靠网络的环境下，没有线性一致性约束，可能会出现如下问题:

Case 1：写后仍然读旧值（写后读问题）

C1 已经成功写入了 10，但 C2 后来发起的读操作居然还读到旧值。

Case 2：并发写的结果不可推理

两个写操作并发进行。

线性一致性的定义

所有操作看起来像是在某个全局线性顺序下瞬时执行的。

换句话说，线性一致性保证:

  1. 写后读：一个写操作完成后，所有后续读操作必须能看到它
  2. 不回退：一旦某个状态被观察到，系统不能再回到更早的状态
  3. 全局一致：所有客户端对操作顺序有统一的认知

示例

在此期间，如果没有其他 Client 修改该 key，线性一致性要求 C2 读到的 value 一定是 C1 写入的 value。

核心价值

线性一致性给并发/分布式系统提供了一个**简单、可推理的操作模型

思考

如果一个 client 在持有锁时崩溃了，那么这把锁就永远不会释放。在更加真实的设计中，client 在持有锁时会被附上一条 lease (租约)，租约到期后, lock server 会主动释放 client 的 lock。由于在这个实验中，client不会崩溃，所以在现有的实现中，可以不考虑这个问题。
