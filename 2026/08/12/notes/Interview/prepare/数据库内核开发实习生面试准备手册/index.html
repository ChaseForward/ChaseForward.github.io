二、数据库内核 · 缓冲池管理（高频深挖区）

7. 缓冲池的完整工作流程是什么？

提示：从执行器请求页面开始：查页表 → 命中则pin_count++ → 未命中则找空闲页框 → 无空闲则选victim（pin_count必须为0）→ 脏页写回 → 提交磁盘读请求（异步）→ 后台线程完成IO → 更新页表 → pin_count=1 → 返回。执行器用完unpin（pin_count–，标脏但不立即写回）。

【你的回答】

8. pin_count 的作用是什么？如果忘记 unpin 会怎样？

提示：pin_count是原子变量，>0表示页面正被占用，不允许驱逐。忘记unpin会导致页框泄漏（page leak），最终空闲页框耗尽，请求新页的线程被阻塞。

【你的回答】

9. 你为什么选择实现 ARC 而不是 LRU？ARC 解决了 LRU 的什么问题？

提示：LRU两个问题：预读失效、缓冲池污染（全表扫描冲掉热点）。ARC维护四条链表（T1最近访问一次、T2最近访问多次、B1/B2 ghost历史链表），通过ghost命中情况自适应调节参数p，区分冷数据和热数据。

【你的回答】

10. ARC 中的参数 p 是什么？如何自适应调整？调错会怎样？

提示：p是T1（recency侧）的目标大小。B1 ghost命中→p增大（说明最近一次的页有价值）；B2 ghost命中→p减小（说明频繁访问的页该多缓存）。p固定不动会退化为纯LRU或纯LFU，失去自适应能力。

【你的回答】

11. ARC 的并发控制是怎么做的？（快手深挖）

提示：这是你的失分点。不要只说”上锁”。要回答：全局锁的粒度问题 → 快手面试官提示的正确方向：分区（Sharding），每个分区独立维护链表+一把锁，按页号哈希到不同分区，减少锁冲突。先承认你原版实现可能是全局锁，然后讲优化方向。

【你的回答】

12. 如果多线程并发访问 LRU/ARC，除了加锁还有什么办法提升性能？

提示：分区锁（每个分区一个锁，按key/page_id哈希）→ 无锁队列/环形缓冲区 → RCU（Read-Copy-Update）→ 读写锁（但读锁也会阻塞写）。最实际的工业方案是分区。

【你的回答】

13. 页表是做什么的？ARC 怎么快速找到一个页面对应的指针？（快手深挖）

提示：页表是页号→页框（frame_id）的映射，通常用 unordered_map 或哈希表。快速查找靠哈希表O(1)。要清楚说出：页表存储的是 page_id 到 frame 的映射，frame 里包含页面内容+元数据（pin_count, dirty等）。

【你的回答】

14. Disk Scheduler 为什么要异步？消息队列怎么设计？

提示：同步会阻塞请求线程。异步让调用者提交请求后立即返回做别的事，后台线程完成IO后通知。消息队列用多生产者-单消费者模型，mutex + condition_variable 保护，请求封装为结构体（page_id, frame, is_write等）。

【你的回答】

15. 多个线程同时请求同一个不在内存的页面，如何避免重复读取？

提示：用哈希表记录”正在加载中”的页面（page_id → promise/condition_variable）。第一个线程发起读请求并加入哈希表，后续线程发现已在加载中，阻塞等待（条件变量），加载完成后由第一个线程唤醒。

【你的回答】

三、数据库内核 · B+Tree 索引（高频深挖区）

16. 为什么数据库索引用 B+Tree 而不是红黑树/哈希表/跳表？

提示：B+Tree扇出大→树高低→磁盘IO少；节点对齐page（4KB/8KB），局部性好；叶子节点链表支持范围查询。红黑树高度高、不适合磁盘；哈希表不支持范围查询；跳表虽支持范围查询但B+Tree更矮胖、磁盘IO更少。

【你的回答】

17. B+Tree 是怎么做到并发访问的？讲一下 Latch Crabbing 的完整流程

提示：搜索：自上而下拿读锁，拿到子节点读锁后释放父节点读锁。写操作：乐观路径（下行读锁，叶子节点直接加写锁，判断safe则操作）→ 悲观路径（若叶子不安全，回退，自顶向下拿写锁，确认子节点safe才释放父节点写锁）。强调：读锁下判断安全不可靠，因为释放读锁到拿写锁之间有时间窗口。

【你的回答】

18. 什么是 safe 节点？为什么写锁下才能判断 safe？

提示：插入safe：节点未满，不会分裂；删除safe：节点超过半满，删除后不会下溢。读锁下判断safe后，释放读锁→拿写锁期间，其他线程可能插入导致节点变满，所以不可靠。

【你的回答】

19. 讲一下 B+Tree 的分裂与合并原理，尽可能讲细节

提示：分裂：叶子节点满时，将右半部分复制到新节点，中间key上提到父节点；若父节点也满，递归分裂；若根节点分裂，树高+1。合并：节点下溢时，先看相邻兄弟能否 redistribute（借一个，轻量），不能则 merge（两节点合并，父节点删分隔key，可能递归向上）。

【你的回答】

20. 墓碑（Tombstone）机制是怎么做的？为什么能减少 Merge？

提示：删除时不物理移除，而是打标记。好处：延迟物理回收，多个删除累积到阈值再批量merge，避免每次删除都触发节点合并和结构调整，降低锁竞争和写放大。代价：空间放大、扫描需过滤墓碑。墓碑参与MVCC版本链（可能复活）。

【你的回答】

21. 墓碑缓冲区保存的是什么？什么时候真正回收墓碑？（快手深挖）

提示：保存被逻辑删除的键值对索引/位置。回收时机：1) 墓碑缓冲区满，淘汰最早删除的；2) 两个叶子节点合并时回收。要讲清楚你用的是 vector 还是其他结构存储墓碑。

【你的回答】

22. 删除逻辑的完整流程是什么？（快手深挖）

提示：搜索到目标key → 打墓碑标记（或插入删除记录）→ 不立即修改节点大小 → 定期/阈值触发时批量清理。如果面试官要求详细到代码层面，要能说清楚是在叶子节点的 entries 数组中做标记，还是单独维护一个 tombstone 数组。

【你的回答】

23. Merge 与 Redistribute 的触发条件和区别？

提示：删除后节点低于下界时触发。先检查兄弟：兄弟借出一个后仍高于下界 → redistribute（从兄弟借一个键值对，更新父节点分隔key，树高不变）。兄弟也接近下界 → merge（两节点合并成一个，父节点删key，可能递归向上，可能降树高）。

【你的回答】

四、数据库内核 · 查询执行器与优化器

24. 讲一下 Volcano Iterator 模型的原理和优缺点

提示：每个算子实现 Next() 接口，父算子调用子算子的 Next()，每次拉取一条tuple，数据自底向上流动。优点：逻辑清晰、易于组合、内存占用低（流式）。缺点：虚函数调用开销大、分支预测失败、不利于SIMD。向量化执行（一次一批）可优化。

【你的回答】

25. 一条 SQL 语句在数据库中的完整执行流程是什么？

提示：SQL字符串 → Parser生成语法树（AST）→ Binder语义绑定（检查表名、列名、类型）→ Planner生成逻辑执行计划 → Optimizer优化（选择索引、选择Join算法、下推谓词）→ Executor执行算子 → 访问存储层（缓冲池/B+Tree）。

【你的回答】

26. SeqScan 和 IndexScan 有什么区别？什么情况下会触发 SeqScan → IndexScan 的优化？

提示：SeqScan全表扫描，逐行读取；IndexScan通过B+Tree索引定位到满足条件的行。触发条件：查询有过滤条件（WHERE）、且过滤条件对应索引key、且优化器估算索引扫描代价小于全表扫描。注意：IndexScan的前提是”先建了索引”，不是查询时生成索引。

【你的回答】

27. 讲一下 IndexScan 的整体流程

提示：从根节点开始，用索引key在B+Tree中搜索 → 找到对应叶子节点 → 根据索引存储的指针（如RID/RowID）去数据页取完整记录 → 返回给上层算子。如果是覆盖索引（Covering Index），则不需要回表。

【你的回答】

28. Nested Loop Join 和 Hash Join 的原理与区别？

提示：NLJ：外层表每行 × 内层表每行，O(m×n)，适合内表极小或有索引的场景。Hash Join：小表建哈希表（Build），大表逐行探测（Probe），O(m+n)，适合等值Join且内存能放下构建表。内存放不下时分桶落盘（Grace Hash Join）。

【你的回答】

29. Hash Join 中，遍历大表时在做什么？怎么判断相等？（快手深挖）

提示：Probe阶段：取大表一行 → 提取Join Key → 计算哈希值 → 在哈希表对应桶中查找 → 逐个比较是否equal（因为哈希冲突，必须逐key比较）。要具体说出”计算哈希→定位桶→遍历桶内元素→比较key相等→拼接结果”。

【你的回答】

30. 外部归并排序（External Merge Sort）的原理？

提示：数据量超过内存时，分批读取排序生成多个有序run → 用最小堆/多路归并合并这些run → 若run太多无法同时加载，先归并部分run生成更大run，递归进行。二路归并是基础，实际可用多路归并减少pass数。

【你的回答】

五、数据库内核 · MVCC 与事务管理（高频深挖区）

31. 数据库中引入 MVCC 主要是解决什么问题？（海致致命题）

提示：不是保证 Consistency！ 正确答案是：实现读写互不阻塞，提高并发吞吐量。读事务读历史版本快照（不阻塞写），写事务修改最新版本（不阻塞读）。在快照隔离（SI）下解决脏读、不可重复读、幻读。只有写-写冲突才需要检测/回滚。

【你的回答】

32. MVCC 的整体架构是什么？版本如何组织？

提示：不是存储多副本，而是 base tuple + undo log 版本链。修改时：将旧值写入undo log，形成链表（最新→旧版本）。每行记录通过回滚指针串联历史版本。

【你的回答】

33. 可见性如何判断？ / 如何根据时间戳判断可见版本？（快手深挖）

提示：事务开始时分配 read_ts（快照时间戳）。判断某版本：该版本的创建时间戳（begin_ts）≤ read_ts 且 失效时间戳（end_ts）> read_ts（或未失效）。如果版本创建者事务未提交，对当前事务不可见。若当前版本不可见，沿undo链回溯。

【你的回答】

34. 时间戳是怎么分配的？具体机制是什么？（快手深挖）

提示：事务管理器维护全局单调递增的时间戳计数器。事务开始时原子地获取当前计数器值作为 read_ts。写事务提交时获取 commit_ts。注意：要区分 read_ts 和 commit_ts，以及临时时间戳（如事务ID左移用于未提交标识）。

【你的回答】

35. 快照隔离（Snapshot Isolation, SI）解决了什么问题？无法解决什么问题？

提示：解决：脏读、不可重复读、幻读。无法解决：写偏差（Write Skew）、不可串行化。SI只检测写-写冲突（First-Committer-Wins），不检测读-写冲突。

【你的回答】

36. 什么是 Write Skew（写偏差）？举个例子

提示：经典例子：医生值班约束”至少一人在岗”。T1读B在岗→A离岗；T2读A在岗→B离岗。两事务并发提交后，无人在岗，违反约束。因为各自读了对方要写的子集再写，SI不检测这种冲突。

【你的回答】

37. 可串行化（Serializable）如何实现？与 SI 的区别？

提示：乐观后向校验：写事务提交前，检查在当前事务之后已提交/未提交的写事务，通过谓词条件判断是否冲突（如幻读）。SI是乐观并发控制的一种，但不保证串行化。2PL（两阶段锁）可保证严格可串行化，但读写互斥、可能死锁。

【你的回答】

38. MVCC 的垃圾回收（GC）怎么做？

提示：找到当前所有活跃事务中最小的 read_ts（watermark），比 watermark 更小的旧版本都可以安全删除。BusTub中用后台线程定期扫描并回收。

【你的回答】

39. MVCC 与 2PL 的对比？

提示：MVCC：读写不互斥，无死锁，读多写少吞吐高，有存储开销和GC负担。2PL：读写互斥，需死锁检测，并发度低，但可严格可串行化。

【你的回答】

40. MVCC 在事务验证中具体验证哪些冲突？

提示：只验证写-写冲突（两个事务修改同一行，先提交者获胜，后提交者abort）。不验证读-写冲突（这是SI下可能发生写偏差的原因）。

【你的回答】

41. MySQL / InnoDB 的 MVCC 是怎么实现的？与你实现的有什么区别？

提示：InnoDB每行隐藏字段：DB_TRX_ID（最近修改事务ID）、DB_ROLL_PTR（回滚指针）。通过ReadView（活跃事务ID列表）判断可见性。你的实现（BusTub风格）：显式版本链（begin_ts/end_ts），与PostgreSQL类似。

【你的回答】

42. ACID 分别是怎么保证的？

提示：A（原子性）：undo log，事务失败或abort时回滚。C（一致性）：应用层约束（外键、唯一索引）+ 事务隔离性保证。I（隔离性）：MVCC/SI。D（持久性）：WAL（redo log），先写日志再刷脏页。

【你的回答】

六、分布式系统 · Raft 与 KV 存储

43. 什么是 Raft 协议？简单展开讲讲

提示：强一致性的日志复制协议，保证线性一致性。三个子问题：Leader选举、日志复制、快照压缩。核心是”强势Leader”，所有读写经Leader，Follower只接收复制。

【你的回答】

44. Raft 为什么只能有一个 Leader？如何避免脑裂？

提示：多Leader会导致数据不一致。通过term单调递增+选举超时机制+过半票决保证任意时刻只有一个有效Leader。同一term每节点最多投一票，当选需多数派。

【你的回答】

45. Leader 选举的完整流程？为什么需要随机超时？

提示：Follower超时未收到心跳→转为Candidate→自增term→投自己→向其他节点发RequestVote。随机超时避免多个节点同时发起选举导致分裂投票（Split Vote）。RequestVote会重置其他节点超时时间。

【你的回答】

46. 一个节点要成为 Leader，需要哪些约束？

提示：1) 获得过半票数；2) 选举超时随机；3) 日志尽可能新（最后一条日志的term更大，或term相同但索引更大），防止已提交日志被覆盖。

【你的回答】

47. 日志复制的完整流程？日志冲突如何恢复？

提示：Leader通过AppendEntries RPC复制日志。每个Follower维护nextIndex（Leader认为该Follower需要的下一条日志索引）。若Follower拒绝（prevLogTerm不匹配），Leader递减nextIndex直到匹配，然后批量复制。优化：Follower返回冲突term及该term第一条日志位置，Leader直接跳到该位置。

【你的回答】

48. commitIndex 和 lastApplied 的区别？

提示：commitIndex：日志已复制到多数派，可以提交。lastApplied：日志已应用到状态机。满足 lastApplied ≤ commitIndex。Leader只能直接提交当前term的日志（Raft安全性，Figure 8）。

【你的回答】

49. Snapshot 机制为什么能减少日志？InstallSnapshot 流程？

提示：日志无限增长会导致重启慢、占空间。Snapshot把已应用到状态机的数据持久化，附带lastIncludedIndex/Term，之前的日志可截断。InstallSnapshot：Follower落后太多（nextIndex < Leader快照点），Leader直接发快照文件，Follower接收后替换本地状态机+日志。

51. At-Most-Once 语义如何保证？

52. 网络分区恢复后会发生什么？Leader 崩溃时已接收但未提交的请求会怎样？

56. 讲一下两阶段提交（2PC）的流程和缺陷

提示：阶段一（Prepare）：协调者问所有参与者能否提交，参与者执行本地事务、写undo/redo、锁定资源，返回Yes/No。阶段二（Commit/Rollback）：全Yes则发Commit，任一No则发Rollback。缺陷：同步阻塞（参与者持锁等待）、协调者单点故障、脑裂（部分收到Commit部分没收到）。

57. 了解 Percolator 模型吗？（TiDB 在用）

八、存储引擎 · LSM-Tree / RocksDB / MySQL

61. 了解过 LevelDB / RocksDB 吗？LSM-Tree 的核心原理是什么？（海致致命题）

提示：解决B+Tree写放大问题。核心：随机写变顺序写。写入先进内存MemTable（跳表/红黑树）→ 满后刷盘为Immutable SSTable → 后台Compaction合并多层SSTable（L0, L1, L2…）。读：先查MemTable→Immutable→各层SSTable（从新到旧）。用Bloom Filter加速。WAL保证崩溃安全。

【你的回答】

62. LSM-Tree 和 B+Tree 怎么选？

提示：读多写少、需范围查询、二级索引 → B+Tree（OLTP）。写多读少、顺序写友好 → LSM-Tree（日志、时序）。混合负载看比例，也可结合（TiDB：TiKV用LSM，TiFlash用列存）。

【你的回答】

63. LSM-Tree 的 Compaction 策略有哪些？

提示：Level Compaction（默认，层间合并，空间放大可控但写放大高）；Universal Compaction（时间窗口内合并，读放大小但空间放大高）；FIFO Compaction（保留最近数据，类缓存）。

【你的回答】

64. RocksDB 有哪些关键特性？

提示：多线程Compaction、列族（Column Family，独立MemTable/SSTable，共享WAL）、多种Compaction策略、前缀布隆过滤器、快照（基于序列号实现MVCC）、事务支持（乐观/悲观锁）。

【你的回答】

65. RocksDB 的 WAL 和 MemTable 的关系？

提示：写请求先写WAL（顺序写磁盘，持久化），再写MemTable（内存）。崩溃后重放WAL重建MemTable。
