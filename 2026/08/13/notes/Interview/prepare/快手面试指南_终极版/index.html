这是 MIT 6.5840 的分布式系统实验，我基于 Raft 一致性协议实现了线性一致的 KV 存储。

Raft 模块我实现了 Leader 选举、日志复制、持久化和快照机制。
Leader 选举使用随机超时避免活锁；日志复制通过 nextIndex 探测找到冲突点，
批量复制日志；快照机制对已提交日志做压缩，避免日志无限增长。

在 Raft 之上我构建了多副本 KV 存储，实现 Get/Put 接口。
为了保证 At-Most-Once 语义，客户端请求携带 ClientID + SequenceNumber，
服务端维护去重表，同一个请求至多执行一次。

网络分区场景下，旧 Leader 会自动退位，新 Leader 通过更高 term 接管，
保证已提交日志不会被覆盖，未提交日志可能被新 Leader 覆盖。

LSM-Tree（Log-Structured Merge-Tree）是为了解决 B+Tree “读快写慢”的问题。

B+Tree 的写瓶颈：

  • 每次插入都要找到叶子节点 → 多次随机 IO
  • 可能触发页分裂 → 更新父节点 → 更多随机 IO
  • 一句话：B+Tree 的写 = 多次磁盘随机跳转

LSM-Tree 的核心思想：

  • 把”随机写磁盘”变成”顺序写磁盘”
  • 写入先进入内存中的 MemTable（有序结构，如跳表）
  • MemTable 满了之后刷到磁盘，变成一个不可变的 SSTable（Sorted String Table）
  • 磁盘上的 SSTable 按层组织（L0, L1, L2…），下层数据量更大
  • 后台线程定期做 Compaction：合并相邻层的 SSTable，去重、删除过期数据

读操作：

  • 先查 MemTable → 再查不可变 MemTable → 再按时间倒序查各层 SSTable
  • 因为数据可能分散在多个 SSTable，读性能比 B+Tree 差
  • 为了加速读，引入 Bloom Filter 快速判断 key 是否在某层

写操作：

  • 纯内存写入 + 顺序刷盘，写性能极高
  • WAL（Write-Ahead Log）保证崩溃安全：先写日志，再写 MemTable

权衡：

  • 写放大：Compaction 会反复重写数据
  • 读放大：需要查多层 SSTable
  • 空间放大：旧版本数据在 Compaction 前一直存在

RocksDB 是 Facebook 基于 LevelDB 优化的高性能嵌入式 KV 存储引擎，基于 LSM-Tree。

关键优化：

  1. 多线程 Compaction：LevelDB 单线程，RocksDB 支持多线程并行 Compaction
  2. 列族（Column Family）：不同列族独立 MemTable 和 SSTable，共享 WAL
  3. 多种 Compaction 策略：
    • Level Compaction（默认）：层与层之间合并，空间放大小但写放大高
    • Universal Compaction：时间窗口内合并，读放大小但空间放大高
    • FIFO Compaction：只保留最近数据，类似缓存
  4. 前缀布隆过滤器：对范围查询友好
  5. 快照（Snapshot）：基于序列号实现 MVCC，读快照不阻塞写
  6. 事务支持：基于乐观锁 / 悲观锁的事务

与 MySQL InnoDB 对比：

  • InnoDB 基于 B+Tree，适合读多写少、需要范围查询和二级索引的 OLTP 场景
  • RocksDB 基于 LSM-Tree，适合写多读少、顺序写友好的场景（如日志、时序数据）
  • MyRocks：MySQL 的 RocksDB 存储引擎，用 RocksDB 替代 InnoDB

单机事务靠 ACID，分布式事务要跨多个节点保证 ACID，难度在于网络不可靠。

核心挑战：

  1. 原子性：多个节点的操作要么全成功，要么全回滚
  2. 一致性：分布式环境下数据一致性（CAP 理论）
  3. 隔离性：并发事务的隔离级别
  4. 持久性：数据不丢失

经典方案：

参与者：Coordinator（协调者）+ 多个 Participant（参与者）

阶段一（投票）：

  • Coordinator 向所有 Participant 发送 Prepare 请求
  • Participant 执行本地事务，写 undo/redo 日志，锁定资源
  • Participant 返回 Yes（可以提交）或 No（无法提交）

阶段二（提交/回滚）：

  • 如果所有 Participant 返回 Yes，Coordinator 发送 Commit
  • 如果有任一 Participant 返回 No，Coordinator 发送 Rollback
  • Participant 收到 Commit 后真正提交，释放锁

问题：

  1. 同步阻塞：Participant 在等 Coordinator 决策期间一直持有锁
  2. Coordinator 单点故障：如果 Coordinator 在第二阶段挂了，Participant 一直阻塞
  3. 脑裂：Coordinator 给部分节点发 Commit，部分节点没收到

解决：3PC（增加 PreCommit 阶段，引入超时机制），但工业界很少用

基于 2PC + MVCC 的分布式事务模型，依赖中心化的 Timestamp Oracle（TSO）。

三列存储：

  • data：实际数据
  • lock：锁信息，标识哪个事务在修改
  • write：提交记录，指向具体版本

流程：

  1. Prewrite（预写）：

    • 选出一个 Primary Key，其余为 Secondary Keys
    • 在 Primary 上写 lock，在 data 列写数据（带 start_ts）
    • 在 Secondary 上也写 lock 和 data
    • 如果某个 Key 已被其他事务锁定，Prewrite 失败，事务回滚

  2. Commit：

    • 先提交 Primary：删除 lock，在 write 列写提交记录（带 commit_ts）
    • 再异步提交 Secondary：同样删除 lock，写 write 列
    • 如果 Secondary 提交失败，靠后续事务清理（懒清理）

优点：去中心化 Coordinator，利用 MVCC 实现 SI
缺点：依赖 TSO，跨数据中心时延迟高；长事务锁冲突严重

把单机 BusTub 扩展为分布式数据库，核心要解决三个问题：

  1. 数据分片（Sharding）：

    • 按表的主键范围（Range）或哈希（Hash）分片
    • 每个分片是一个 Raft Group，用 Multi-Raft 管理
    • 参考 TiDB：TiKV 按 Region（默认 96MB）分片，每个 Region 是一个 Raft Group

  2. 分布式事务：

    • 跨分片事务需要 2PC 或 Percolator 模型
    • 单分片事务可以直接用本地 MVCC
    • 需要全局时钟（TSO）保证快照隔离

  3. 查询层：

    • 增加 SQL 解析层，识别查询涉及的分片
    • 聚合算子需要分布式执行（如分布式 Hash Join、分布式 Aggregation）
    • 参考 TiDB：TiDB Server 负责 SQL 解析和分布式执行计划生成

  4. 元数据管理：

    • 需要中心化的元数据服务（如 TiDB 的 PD，负责调度、负载均衡、全局时钟）
    • 元数据服务本身也要高可用（通常用 Raft 或 etcd）

MySQL 主从复制（Master-Slave Replication）是异步/半同步的日志复制机制。

三种日志：

  1. redo log（InnoDB 层）：物理日志，记录页的修改，用于崩溃恢复（保证持久性 D）
  2. undo log（InnoDB 层）：逻辑日志，记录修改前的值，用于回滚和 MVCC
  3. binlog（Server 层）：逻辑日志，记录 SQL 语句或行变更，用于主从复制和时间点恢复

主从复制流程：

  1. Master 写事务：先写 redo log（prepare），再写 binlog（commit），最后引擎提交
  2. Slave 的 IO Thread 主动连接 Master，请求 binlog
  3. Master 的 Dump Thread 发送 binlog 给 Slave
  4. Slave 的 IO Thread 将 binlog 写入本地 Relay Log
  5. Slave 的 SQL Thread 重放 Relay Log 中的事件，应用到本地数据库

复制模式：

  • 异步复制：Master 不等待 Slave 确认，性能最好但可能丢数据
  • 半同步复制：Master 至少等待一个 Slave 收到 binlog 并写入 Relay Log 才返回成功
  • 组复制（MGR）：基于 Paxos 的一致性复制，自动故障转移

与 Raft 的区别：

  • MySQL 主从：Slave 主动拉取，异步/半同步，最终一致性
  • Raft：Leader 主动推送，强一致性（线性一致性），基于多数派

海致面试官问：”数据库中引入 MVCC 主要是解决什么问题？”
你答：”保证一致性（Consistency）” ❌❌❌
面试官提示：”读不阻塞写” ✅

MVCC（Multi-Version Concurrency Control）的核心目的是：
在高并发场景下，实现读写互不阻塞，提高并发吞吐量。

具体解决什么问题：

  1. 读不阻塞写：读事务读历史版本快照，不需要加锁，不会阻塞写事务
  2. 写不阻塞读：写事务修改最新版本，读事务仍然可以读旧版本快照
  3. 避免脏读、不可重复读、幻读（在 SI 级别下）

注意：MVCC 不直接保证 Consistency（一致性）。
Consistency 是应用层通过约束（如外键、唯一索引）保证的。
MVCC 保证的是 Isolation（隔离性），通过多版本实现非阻塞的并发控制。

与 2PL 的对比：

  • 2PL：读写互斥，需要加锁，可能死锁，并发度低
  • MVCC：读写不互斥，不需要锁（写-写仍要冲突检测），并发度高
  • 代价：存储开销（维护版本链）、GC 负担、长事务问题

static 的四种用法：

  1. 局部静态变量：

    • 存储在静态存储区，生命周期贯穿程序始终
    • 只初始化一次，下次进入函数时保持上次值
    • C++11 起初始化是线程安全的（编译器加锁），但并发读写不安全

  2. 全局静态变量 / 静态函数：

    • 限制链接属性为内部链接（Internal Linkage）
    • 只在当前翻译单元（.cpp + 头文件）可见
    • 不同 .cpp 文件可以定义同名 static 全局变量，互不干扰
    • 注意：如果头文件中定义 static 变量，被多个 .cpp include，
      每个 .cpp 会有独立副本，不是共享的！

  3. 类静态成员变量：

    • 属于类，不属于对象，所有对象共享
    • 类内声明，类外初始化（除非 constexpr / const integral inline）
    • 生命周期：程序启动后 main 之前初始化，程序结束销毁
    • 多线程：初始化线程安全（C++11），但并发读写需加锁或原子操作

  4. 类静态成员函数：

    • 没有 this 指针，不能访问非静态成员
    • 可以用类名::函数名() 调用

核心概念：

  • 左值（Lvalue）：有名字、可取地址的对象，如变量 a
  • 右值（Rvalue）：临时对象、字面量，如 42、std::move(a) 的结果
  • 右值引用（T&&）：绑定到右值，允许”窃取”资源

std::move() 的本质：

  • 只做类型转换，将左值强制转为右值引用
  • 不移动任何数据！真正的移动发生在移动构造函数 / 移动赋值运算符中
  • 移动后原对象处于”有效但未指定状态”，不应再使用

移动构造函数的实现要点：

  1. 窃取源对象的资源指针（如 buf_ = other.buf_）
  2. 把源对象指针置空（other.buf_ = nullptr）
  3. 防止自赋值检查
  4. noexcept 标记（重要！std::vector 扩容时只有 noexcept 移动构造才会用移动而非拷贝）

完美转发 std::forward：

  • 在模板中保持参数的左值/右值属性
  • 配合万能引用 T&& 使用

三种智能指针：

  1. unique_ptr：独占所有权，不能拷贝，只能移动

    • 开销：几乎为零（就是一个裸指针 + deleter）
    • 场景：工厂函数返回值、RAII 资源管理

  2. shared_ptr：共享所有权，引用计数

    • 控制块（Control Block）存储：引用计数（强引用、弱引用）、删除器、分配器
    • 引用计数是原子操作（线程安全），但指向的对象本身不是线程安全的
    • 循环引用问题：A 持有 shared_ptr，B 持有 shared_ptr，导致内存泄漏
    • 解决：一方改用 weak_ptr，打破循环

  3. weak_ptr：弱引用，不增加引用计数

    • 用于观察 shared_ptr 管理的对象，不影响生命周期
    • lock() 获取 shared_ptr，如果对象已销毁返回空
    • 场景：缓存、观察者模式、打破循环引用

注意：

  • shared_ptr 的引用计数线程安全 ≠ 对象线程安全
  • 不要用裸指针初始化多个独立的 shared_ptr（会导致多个控制块、双重释放）
  • 优先用 make_shared / make_unique，减少分配次数、异常安全

层次模型：

  • 磁盘：持久化存储，最慢
  • 内存（RAM）：易失性，较快
  • CPU Cache（L1/L2/L3）：更快，硬件管理一致性（MESI 协议）
  • 寄存器：CPU 内部，最快

数据不一致的场景：

  1. 寄存器 vs 内存：

    • 变量从内存加载到寄存器后，如果只在寄存器修改而不写回内存，两者不一致
    • volatile 关键字：告诉编译器不要优化，每次读写都走内存（但不保证原子性）

  2. 内存 vs 磁盘：

    • 数据库中，数据页在内存修改后（脏页），如果未刷盘就崩溃，内存和磁盘不一致
    • 解决：WAL（Write-Ahead Log），先写日志再改数据页，崩溃后重放日志

  3. CPU Cache 不一致：

    • 多核 CPU，每个核有独立 L1/L2 Cache
    • 一个核修改了 Cache Line，另一个核读到的可能是旧值
    • 解决：MESI 协议（Modified/Exclusive/Shared/Invalid）
    • False Sharing：两个线程修改同一个 Cache Line 的不同变量，导致频繁缓存失效
      • 解决：对齐到 64 字节（Cache Line 大小），如 alignas(64)

传统数据库：单体架构，存储计算耦合，扩缩容困难
Cloud Native 数据库：存储计算分离，弹性伸缩，高可用

核心特征：

  1. 存算分离：

    • 计算节点无状态，只负责 SQL 解析、执行计划、事务协调
    • 存储节点负责数据持久化，通常用分布式文件系统或对象存储
    • 优势：计算和存储独立扩缩容，计算节点故障恢复快

  2. 共享存储（Shared Storage）vs 共享 nothing（Shared Nothing）：

    • Shared Storage：如 Aurora，多个计算节点共享一份存储，日志即数据库
    • Shared Nothing：如 TiDB，每个节点独立存储，通过 Raft 同步

  3. 弹性伸缩：

    • 计算层：根据负载自动增减计算节点（Kubernetes + Operator）
    • 存储层：自动分片、自动迁移、自动均衡

  4. 高可用：

    • 计算节点无状态，故障后快速切换到备用节点
    • 存储层多副本（Raft / Paxos），自动故障转移

九、附录：储备题库速查（A/B/C 级）

A 级（本场重点）

  • LSM-Tree 原理：MemTable → Immutable MemTable → SSTable → Compaction
  • RocksDB 特性：多线程 Compaction、Column Family、多种 Compaction 策略、WAL
  • 分布式事务：2PC 流程与缺陷、Percolator 模型（Prewrite + Commit）、TSO
  • MySQL 复制：binlog / redo log / undo log 区别、主从复制流程、半同步复制
  • MVCC 目的：读不阻塞写、写不阻塞读、提高并发吞吐（不是保证 Consistency！）
  • Cloud Native 数据库：存算分离、Shared Storage vs Shared Nothing、弹性伸缩
  • 墓碑机制：逻辑删除、延迟回收、降低合并频率、空间放大代价
  • Raft 优化：批量日志、流水线、nextIndex 快速回退、PreVote 避免网络分区干扰

B 级（有思路即可）

  • io_uring vs epoll：io_uring 共享内存环，减少系统调用
  • False Sharing：Cache Line 伪共享，alignas(64) 解决
  • MyRocks：MySQL 的 RocksDB 存储引擎，替代 InnoDB
  • TiDB 架构：TiDB Server（SQL 层）+ PD（元数据/调度）+ TiKV（存储/Raft）
  • C++ 移动构造 noexcept：vector 扩容时只有 noexcept 才用移动
  • shared_ptr make_shared 优势：一次分配（控制块 + 对象），异常安全

C 级（了解概念）

  • OceanBase：蚂蚁自研分布式数据库， share-nothing 架构
  • Golang vs C++：GC vs 手动内存管理、Goroutine vs 线程
  • 数据库故障定位：慢查询、EXPLAIN、GDB、core dump
  • 三年规划：一年独立模块 / 两年核心链路 / 三年技术方向

最后提醒：

  1. 自我介绍和项目介绍是基本功，必须背熟，不能现场组织语言
  2. LSM-Tree / RocksDB / 分布式事务 / MySQL 复制 是本场最大变量，必须拿下
  3. MVCC 的目的是读写不阻塞，不是保证 Consistency，不要再答错！
  4. 埋钩子：每个回答结尾留一个”引子”，引导面试官问你准备好的问题
  5. 自信：你已经做了两个硬核项目，基础是扎实的，缺的只是知识广度

祝你明天快手面试顺利，拿下 offer！🎯🔥
